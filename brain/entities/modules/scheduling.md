# Schedule 排程中心（v2.7）

**定位**：課級 Skill 定時執行（Nav 第 6 位，獨立 Tab）。是[被動查詢原則](ai-chat.md)的**唯一例外**，主動性受三重約束：(1) 執行的是課員預設的 Skill 與排程，非 AI 自主判斷；(2) 所有 MCP tool 呼叫需人工確認（Human-in-the-loop）；(3) 執行紀錄對全課公開，任何課員可查閱介入。

## 頁面（2026-08-03 決議 23 起：決策收件匣）

**主詞是「事」不是「排程」**，一條規則貫穿全頁：**左欄選什麼，右欄只出現什麼**。

- **左欄＝工作佇列**：`待處理（N）／全部紀錄` 膠囊二選一（唯一的模式切換，預設待處理）→ 兩張分類卡（**待人工決定**／**失敗待確認**，只給類型＋件數）→ 分隔線 → **排程健康**清單（一列＝點＋名稱＋時間，右上「管理」開抽屜）。
- **右欄＝決策台**：header 只講「還有幾件、最久等多久」；第一件展開成決策卡（AI 準備呼叫／參數／依據攤平在同一屏＋動作列），其餘收合成一行。
  - 待人工決定的動作：**同意並繼續／改參數／略過此步**（⚠️ 拒絕執行沒有 UI 入口，見下）。
  - 失敗待確認的動作：**標記已確認／立即重跑／看完整錯誤**（沒有「同意並繼續」——失敗沒有等待中的 AI 步驟）。
  - 點排程健康的一列 → 右欄範圍換成該排程（設定摘要 header ＋ 它自己的執行紀錄），左欄分類卡同時取消選中；**這裡不重複一套決策 UI**，只給一條「到待處理決定 ›」。
- **設定走抽屜**（480px）：排程管理清單 → 編輯／新增**就地換檢視**（左上 `‹ 排程管理` 返回），關掉即回到原本的佇列上下文。
- **本頁沒有任何 AI 對話出口**（2026-08-01 決議 17）。

## 2026-07-25 決議帶來的擴充

依 [agent-skill-tiering](../../concepts/agent-skill-tiering.md)，Schedule 的定位擴大為 **SOP 產出的檔案櫃**：

- **只能掛 SOP**，掛不了輔助判斷（後者每次結果不同、產出是給人看的建議，無人在場即無意義）。新增排程時可選清單只從 **Production 狀態的 SOP 型** 記錄撈
- **執行紀錄要能展示產出物本身**（那份交接報告長什麼樣），不只步驟 —— [Handover 已廢除](handover.md)，其產物改在此檢視
- **含寫入的 SOP 無法真正無人執行**：跑到寫入型 node 會暫停、發通知等人確認才續跑（HITL 前提）。Seed 設排程時須看到「⚠️ 本 SOP 含 N 個需確認步驟，執行到該步驟會暫停並通知你」
- **排程型 SOP 會靜默失效**（資料來源改欄位／系統改 API → 持續產出看似正常但錯誤的報告）→ 需結果異常偵測（與前 N 次比較）＋ 定期自動重跑 dry run
- 知識管理頁的 SOP 詳情提供「設為定期執行」入口，跳轉本頁並預填時間

## 2026-08-01 決議：介入機制改寫（決議 17）

PO 指出兩件事：**未來這一段不打算引入 AI 對話**，而且**「舉手認領」根本不該存在**——該做的是把選項直接攤在介入畫面上，誰點了就記下誰、什麼時候點的。

**新的介入模型**：

| 項目 | 舊 | 新 |
|---|---|---|
| 認領 | 先按「✋ 我來處理」搶鎖，才看得到選項 | **取消**。選項直接攤開，一次點擊完成決定 |
| 選項 | 確認執行 / 拒絕 / 💬 延伸討論 | **確認執行 / 略過此步驟 / 拒絕執行**（拒絕即終止整次執行） |
| AI 出口 | 介入可跳 AI Chat；產出物有「針對這份問 AI」 | **全部移除**，本頁不再有任何 AI 對話出口 |
| 誰能決定 | 搶到鎖的人 | **全課成員（Seed + member）皆可**，不需認領、不指定人 |
| 併發 | 畫面上的暫時鎖，重整即失效，不寫進紀錄 | **先送出者定案（first-write-wins）**。後送出者不受理，畫面轉為已成立的結果 —— **B 推翻不了 A** |
| 可否反悔 | 未定義 | **決定不可變更、不可撤回**。要改只能重跑或另做補救動作 |
| 逾時 | SCH-OQ-1 Claim timeout（建議 15 分鐘） | **不做**。決策點持續等待直到有人決定；升級通知與自動終止後期再補 |
| 理由 | 無輸入 | **拒絕必填**、略過選填 |

**資料模型**：`run.interventions[]` 成為唯一的介入稽核序列，取代舊的 `run.handler` 與 `steps[].decisionBy`（兩者語意重疊、且舊 UI 在決定完成後反而不顯示）。每筆記 `{ actor, action, stepNum, at, reason, toolCall }`，`toolCall` 記下「因為誰的確認，AI 呼叫了哪個 tool、帶什麼參數、回什麼」。**步驟的最終狀態不寫死在資料裡**，改由 `getRunView(run, sessionIvs)` 從介入紀錄推導（拒絕 → 其後全部不執行；略過 → 流程繼續；未決定的第一個需確認步驟＝當前決策點）。`getPendingDecisions(items, decisions)` 是 Nav 紅點與左欄待決定匯總的單一真相。

- 順手修掉兩個 bug：在 A 課新增的排程會殘留到 B 課；切課後右欄掉回空白（`SchedulingPage` 加 `key={persona}`）。

  - **結構化失敗**：`SCH_FAILURE_KIND_CFG`（逾時／權限／資料缺／未知）＋卡在第幾步＋工具＋原始訊息，取代原本一行 `errorMsg`。

  - 時間排序用 `getRunTs()` 從 `startedAt` 推導（`今日`／`昨日`／`MM/DD` 三種寫法），不在 20 筆 mock 上各補一個 `ts` 欄位。`SCH_TODAY` 定義 mock 的今日為 2026-04-21。
- **Phase D 可加入的 Codify（2026-08-01 同日完成）**：
  - **已掛排程的 Codify 在選單中鎖住**並寫明「已掛在排程『XX』（時間）」＋「去看那個排程」連結。這是評估時抓到的真 bug——舊版 `blockReason()` 只看 tier/stage，`sm-eq-008` 已掛 `sch-eq-001` 仍可再選一次，會建出重複排程。
  - **`getSkillScheduleMap()` 成為 Codify↔排程的單一真相**（含本 session 新建的排程）。Schedule 的「不能重複掛」與 Skill 管理的「已掛排程」徽章、刪除警語、詳情「生效資訊」全部改讀這一份，**不再讀 `skill.consumedBy`**——兩邊才不會講不一樣的話。
  - 左欄「＋新增」下方常駐「還有 N 份 Codify 可加入排程」（可點，全掛滿時改顯示「都掛上了」），不必打開 Modal 才知道。
  - Modal 加**搜尋**（名稱／用途／標籤）與**選中後的步驟預覽**（步驟號、名稱、工具、哪幾步標「需人工決定」），不必跳回 Skill 管理。
  - **Codify 詳情「設為定期執行」入口**（brain 自 2026-07-25 起列為未實作）：`onScheduleSkill` → App 設 `newScheduleReq` → 跳排程頁並預開 Modal 且預選那份 Codify；**用完即清**（`onNewScheduleHandled`），否則之後每次回排程頁都會再彈一次。
  - 新建的排程從 `SchedulingPage` local state 提升到 App（`schedExtraItems`，per-persona），Skill 端才看得到剛掛上的排程。
- **Phase E 節點與最終結果（2026-08-01 同日完成）**：
  - **節點明細**：每一步顯示 `tool(params)`／來源系統／資料筆數／耗時；自訂計算步驟顯示它憑什麼算。理由是**試跑畫面本來就看得到工具與資料來源，正式執行沒理由看得比試跑少**。
  - **本次實走路徑**：`getRunPath()` 產出「Step 1 → 2 → 4」＋逐條列出沒走的節點與原因。三種「沒走」分得開：**分支未成立**（引擎沒到）／**人工略過**（人到了、決定不做，算走過但標記出來）／**已拒絕後不執行**。`skip` 這個狀態同時涵蓋前兩者，得靠有沒有介入紀錄才分得出來。
  - ⚠️ **Graph 視角沒有做，改成路徑摘要**。原因：`sm-eq-008` 是唯一有 `graph.edges` 的 Codify，用 `buildGraphLevels()` 分層後是**線性的**（分支是 `2→end`），畫出來與 Timeline 一模一樣；為單一個案做一套 run 版 graph renderer 不划算。路徑摘要用同樣的成本涵蓋全部八個排程。要做 graph 的前提是先有真正會分岔的 Codify 資料。
- **仍未做**：結果異常偵測（與前 N 次比較）、定期自動重跑 dry run、決策等待逾時（SCH-OQ-7，PO 指示先做持續等待）。

## 2026-08-01 決議 18：資訊層級收斂（總覽升為主畫面）

PO 在手機上看實機截圖後指出兩件事：

**① 同一件「有東西卡住」被講太多次**。清點後實際有 7 個表面：Nav 紅點、左欄橫幅、排程卡片紅點＋待決定標籤、總覽置頂區塊、待決定膠囊、通知鈴鐺 N2、決策點面板。PO 判斷是**溝通疲勞**，左欄那一份不需要。

分界標準（本次立的）：**通知是推播、狀態是現況、頁內提示是定位**——三者不同層，但「同一個畫面裡講兩次」就是重複。
- 留：Nav 紅點（人在別頁時唯一觸達）、通知鈴鐺（平台層推播）、排程卡片紅點（清單項目的狀態，不講就不知道是哪一個）、總覽置頂區塊（主頁的行動區）
- 刪：**左欄「本課有 N 件待人工決定」橫幅**——與總覽置頂區塊在同一畫面講一模一樣的話

**② 左欄把三種高度疊在一起**（跨排程警示 → 跨排程頁面 → 單一排程），體感混亂；且原本**預設落點是第一個排程**，等於一進門就鑽進細節。

**新結構**：

| 項目 | 舊 | 新 |
|---|---|---|
| 進入預設 | 第一個排程的詳情 | **執行總覽**（`SCH_ALL`） |
| 左欄組成 | 待決定橫幅＋執行總覽入口＋排程清單 | **只有排程清單**（單一職責） |
| 回總覽 | 左欄再點一次「執行總覽」 | **右欄麵包屑** `排程中心 ／ XX`——「我現在在哪」屬於詳情欄的層級，不該塞在清單上方 |
| 詳情頁的跨排程觸達 | 左欄橫幅 | 麵包屑旁一行 `其他排程還有 N 件待決定`（**只算別的排程**，本排程的決策點就在下方不重複；不另開警示區塊） |

⚠️ **接受的取捨**：人正在看 A 排程細節時，不會被主動告知 B 排程剛卡住（Nav 紅點在本頁看不到）。判斷依據是**排程卡住是分鐘～小時級的事，不是秒級**。麵包屑那行計數是補救，不是第二個警示。

**未違反三欄式佈局**：導覽→列表→詳情三欄都在，只是詳情欄的預設內容從「第一個排程」換成「總覽」。

## 2026-08-01 決議 19：編輯排程（建立／編輯合一 + 變更留痕）

起點是 PO 問「左側清單搜尋」。評估結論是**現在不做**：每課只有 2–4 個排程、一屏看得完，而決議 18 才把左欄瘦成單一職責；門檻設在 **10–12 筆**，屆時比對範圍要含 **Codify 名稱與建立者**（那時的問句是「那份週報掛在哪」而不是「排程叫什麼」）。改為先補本頁最大的操作落差——排程建得出、看得到、決定得了，唯獨**改不了也關不掉**。

**PO 定案**：建立與編輯一起處理、**Seed 與 member 都能做**（不分權限）、但**都要記錄誰最後一次變更**。

| 項目 | 決定 | 理由 |
|---|---|---|
| 名稱 | ✅ 可改 | 新增時預設沿用 Codify 標題；課上習慣叫「早班 SPC 異常日報」不必被綁死 |
| 執行時間 | ✅ 可改 | 唯一真正的編輯需求 |
| **掛的 Codify** | ❌ **不可改** | ①執行紀錄／產出物／`interventions[]` 都是「這份 Codify 做了什麼」，換掉之後同一份歷史前後講不同的事，**決議 17 的稽核序列會斷**；②「一份 Codify 只掛一個排程」是 `getSkillScheduleMap` 的單一真相，換掛會同時改動 Skill 管理的徽章；③要換的正確動作本來就是**停用後另建**，兩邊歷史各自留著 |

**變更留痕**（PO 指定）：`item.lastChange = { by, at, summary }`，summary 寫出「從什麼改成什麼」，顯示在右欄詳情。判準是**排程改的是「沒人在場時 AI 幾點會動作」，比一般設定變更重份量**——延續決議 17「介入痕跡不能因為事情做完就消失」。八筆 mock 排程都補了 `lastChange`。不做完整版本歷史，一行就夠。

## 2026-08-01 決議 20：新增排程只列選得到的（推翻「不可用的也列出來」）

PO 看了實機後指出「已經新增過的不用出現、不能新增進去的也不該出現，畫面會多很多明知不可點的項目，相當困惑」。實測三個課證實比體感更嚴重：

| 課 | 可選 | 鎖住 | 鎖住原因 |
|---|---|---|---|
| ETC 設備課 | **0** | 7 | 已掛排程 2、Skill 型 3、尚未生效 2 |
| ETC 製程課 | 1 | 4 | Skill 型 2、尚未生效 2 |
| MFG 製造課 | 1 | 3 | Skill 型 2、尚未生效 1 |

**推翻的是** [agent-skill-tiering](../../concepts/agent-skill-tiering.md) 立的「不可用的類型不隱藏 —— 看得到、標明原因，Seed 才知道邊界在哪」。**但目的沒被推翻**：一行規則說明同樣講得出邊界，七列鎖頭是把同一句話講七遍——與決議 18 的溝通疲勞同一個模式。而且「哪一種能排程」真正該教的地方是 Skill 管理的兩個分頁（各有小標題在講），邊界教育有自己的家。

**三種鎖住的性質不同，處置不同**（我提的分法，PO 採納）：

| 鎖住原因 | 處置 | 理由 |
|---|---|---|
| 已掛排程 | 隱藏 | 事情已完成，此處無事可做；左欄排程清單本來就列著它（同畫面講兩次）|
| Skill 型不能排程 | 隱藏 | 這是**類型邊界不是狀態**，永遠不會變；在標題寫「選一個 Codify」的清單裡塞滿 Skill，等於要人重讀一條他改不了的規則 |
| 尚未生效 | 隱藏列，改一句常駐說明 | 它**是** Codify、**將來會**能排程、有明確下一步（推完簽核）。若無聲消失，Seed 分不清「我找錯地方」還是「還不能設」 |

**文案由 PO 定稿**：`尚未生效的 Codify 無法設定排程。`（我原本提的是帶筆數與階段的版本，PO 判斷過長）。它講的是**規則不是筆數**，所以**常駐顯示**、不隨狀態變動，要回答的是「我剛寫好的那份為什麼沒出現在這裡」。

⚠️ **順帶校正用字**：查證後發現 **「生效」才是產品的標準用字**（`SkillDetailPage` 的確認生效／已生效／生效資訊／生效範圍、`ChatPage` 的「尚未生效」），**「上線」只出現在排程頁**、是本頁自己造的例外。PO 挑的字比原本的一致。已把排程頁其餘的「上線」一併改為「生效」。

**連帶處理**（同一個「多餘」的病灶）：
- **全掛滿時「＋ 新增」停用**（brain 自決議 18 起掛著的缺口）。鎖住的列拿掉後，打開會是一片空白，比原本更明顯；理由寫在既有的副標「本課已生效的 Codify 都掛上排程了」上。
- **Modal 內的搜尋框移除**。清單縮到 1–3 列後，它就是我在同一 session 反對「左欄加搜尋」的同一個問題——在三列清單上放搜尋框只是多佔一格。
- 清單標題由「選一個 Codify（可加入 N 份）」簡化為「選一個 Codify」（列數即筆數，不必再講一次）；`onJumpSchedule`（「去看那個排程」）隨鎖住的列一起移除，已無觸發點。

**實作狀態（2026-08-01 完成）**：`SchScheduleModal` 的 options 改為只留 `!schBlockReason()` 者。`schBlockReason()` **保留不動**——它仍是「能不能掛」的單一真相，供過濾與計數使用，只是不再逐列渲染理由。**瀏覽器實測 15 項全過**（無鎖頭、三種死列都不出現、常駐提示在、搜尋框已移除、清單由 5 列降為 1 列、仍選得動建得起來、建完後＋新增自動轉停用），無 console error。

### 沒有任何 Codify 可選時（2026-08-01 決議 21）

**空清單的 Modal 進不去**，三個入口都擋住了：「＋ 新增」在 0 份時停用、下方那行入口只在 >0 時才出現、Codify 詳情的「設為定期執行」只在 `stage === 'production'` 分支渲染（Production 且未掛排程 ⇒ 必然 >0 份）。Modal 內的空清單文案是防禦性的，目前跑不到。

**PO 推翻了「常駐副標」的作法（決議 21）**，兩個理由：

**① 一句常駐的話涵蓋不了三種狀況**。0 份可選其實有三種來源，原本寫死的「本課已生效的 Codify 都掛上排程了」只有第一種是對的：

| 本課狀況 | 舊文案 |
|---|---|
| 有 Codify、全掛上排程了 | ✅ |
| **完全沒有 Codify** | ❌ PO 抓到的 |
| **有 Codify、但都尚未生效** | ❌ 同樣錯 |

**② 穩定狀態本來就是「都設定完了」**，每次進來被提醒一次是溝通疲勞（決議 18 的同一條分界）。

**新作法**：停用照舊，理由改成 **hover／點擊才出現的 Tooltip**，文案由 PO 定 —— `目前沒有可設定排程的 Codify`。它**三種狀況下都成立**，所以不做狀態分支。判準是**「為什麼不能按」屬於使用者主動發問時才需要的資訊，不是常駐狀態**。

⚠️ 兩個實作陷阱（都已處理）：停用的 `antd.Button` 不發滑鼠事件，Tooltip 必須包一層 `span` 才觸發得到；**手機沒有 hover**，故 `trigger` 補上 `click`，否則這個解釋在手機上等於不存在（PO 就是在手機上看實機的）。

`>0` 份時那行「還有 N 份 Codify 可加入排程」**保留**：它是「有事可做」的入口、點得下去，與「為什麼不能按」性質不同。**實測 12 項全過**（含手機觸控點擊、點擊不誤開 Modal、移開收起）。

⚠️ 追這條路徑時抓到一個 **pre-existing bug**：`SettingPage` 的 `KnowledgeTab({ p })` 用了 `schedMounts` 與 `onScheduleSkill` 卻沒收進參數，一點 Skill 管理就 `ReferenceError` 白畫面。來源是 Phase D（ddf9c21）接單一真相時漏了最後一跳，而**該輪沒有瀏覽器實測**——這是實測封鎖直接漏掉的第一個真 bug。已修（補收 prop、呼叫處補傳）。

## 2026-08-02 決議 22：總覽的進入點（把導覽補回左欄，把層級畫出來）

PO 試用後指出**進入點是總覽不直覺**：mock 裡左欄第一張卡是「SPC 異常日報」，右欄總覽置頂的待決定也是它，容易誤以為右欄就是那張卡的詳情。

**三個共犯（不是巧合）**：
1. 決議 18 把預設落點改成 `SCH_ALL` 後，**左欄沒有任何項目是選中的**。三欄式的隱含契約是「右欄有內容就有一個選中的左欄項目」，契約一斷，眼睛自動把最靠近的第一張卡讀成右欄的來源。
2. 內容重名：同一個排程名在左欄卡片、置頂 Alert、第一張執行卡出現三次。
3. 總覽與詳情兩個 header 幾乎同構，差別只有「詳情多了麵包屑」——靠某個東西**不存在**來辨識，辨識度本來就低。

**同類系統的三種解**（Windows 工作排程器、GitHub Actions、Dagster、n8n、Airflow、SAP Fiori）：總覽是清單裡一個**可被選中的節點**（工作排程器選根節點才出 Summary、GitHub Actions 的 `All workflows`）／總覽是**獨立 Nav 分頁**（Dagster `Runs`）／**清單本身就是總覽**（Airflow）。**沒有系統做「左欄是清單、右欄預設是一個清單裡選不到的總覽」**。取第一種：獨立分頁語意最乾淨，但排程中心在 Nav 只有一格，要嘛頁內再開一層（決議 18 已否）要嘛動 v3.6 大老闆定的 Nav 順序，以每課 2–4 個排程的規模換不回成本。

**PO 指示**：可以回填，但不要回到決議 18 之前那一版——「問題在 UIUX 設計，不在產品的結構」。

**決議 18 的現象描述對、歸因錯**。它說「左欄疊了三種高度、體感混亂」就砍掉兩種高度；但混亂的來源不是「有三種高度」，是**三種高度沒有被畫成三種高度**。舊版難用的四個原因：①**同一欄兩套選中語彙**（總覽用左藍邊條、排程用整張卡變藍框），認不出彼此是同一組互斥選項；② 三個區塊都長得像可點方塊，但點下去的後果不同層；③ 視覺重量由上往下遞減且倒置，一進門眼睛被釘在最上面那條紅橫幅，而那恰好最不需要優先處理；④ 層級差異只靠一條分隔線，跟卡片間距一樣重。加上總覽那列自己帶紅字統計，它不是導覽是第二條警示。

**本輪立的規則**：**左欄只放導覽，導覽只有兩類（一個總覽 + N 個排程），警示不進左欄。形態不同負責「這不是第 0 個排程」，選中語彙相同負責「這兩者是同一組選項」。**

| 項目 | 決議 18 後 | 決議 22 |
|---|---|---|
| 總覽入口 | 無（右欄主畫面沒有左欄來源）| 左欄置頂一列，扁列 + 圖示，**不帶任何數字、不帶紅點** |
| 選中語彙 | 總覽無、排程用藍框 | **統一「藍框 + 淡藍底」一套**，總覽列與排程卡共用 |
| 層級表達 | 分隔線 | **留白 24px + 「排程清單」分組小標**（分組的語言，不是警示的語言）|
| 待決定卡片 | 紅框 + 粉底 + 紅點 + 標籤 | **只留紅點 + 標籤**——邊框與底色這個通道只表示選中，不兼差表示狀態 |
| 右欄總覽 header | 12px 灰色副標三個數字 | **升成一排 20px 統計**（資訊沒增加、只換視覺權重，故不觸犯決議 18 的溝通疲勞；「待決定」刻意不放，那是下方 Alert 的職責）|

⚠️ **警示橫幅不補回**——決議 18 刪它是對的，本輪只補「導覽入口」那一半。
PO 否決「排程卡片相對總覽縮排」（312px 欄寬太緊，留白 + 小標已足夠）。

### 兩個新增的東西

**① 失敗待確認**（新佇列）。原本失敗只在紀錄裡；現在它是一件「等人的事」，因為**沒有人看過的失敗跟沒發生一樣**。確認是本 session 的 `acks: { [runId]: {by, at} }`，**與 `interventions[]` 分開存**——它不是對 AI 的決定，是「我看過了、別再提醒我」；確認後那筆失敗仍留在執行紀錄裡（`執行失敗（1）` 篩選仍找得到），只是離開佇列。

**② 改參數**（第四種介入）。「同意」與「同意但我改了 AI 要送出去的參數」不是同一件事。`interventions[]` 補 `paramsBefore / paramsAfter`，介入列顯示「（已改參數）」與改前改後——人改寫了工具參數卻不留痕，決議 17 的稽核序列就斷在這裡。**工具本身不可換**（換工具＝換一個步驟，那是改流程不是介入）。

### 兩個 ⚠️

- **「拒絕執行」失去 UI 入口**。設計檔 4a 的動作列只有三顆（同意並繼續／改參數／略過此步），照做的代價是**卡住的執行沒有辦法被人為終止**。`SCH_DECISION_CFG.reject` 與歷史紀錄的 reject 仍渲染得出來（`getRunView` 的推導沒動），要補只是加回一顆按鈕。**下一棒要 PO 拍板**：是接受「只能略過不能終止」，還是把拒絕加回動作列。
- **PO 口述與設計檔不一致的一項，依設計檔**：口述版本說編輯表單裡「哪些步驟要人工確認」是開關（關掉＝AI 直接做不再暫停），但 4d 畫的是**唯讀＋一句「這些步驟一律暫停等人決定，不可關閉；由 Codify 的 Skill 定義」**。依設計檔實作 —— 那個開關等於**允許課級自行解除 HITL**，而 HITL 是排程能存在的前提（本頁三重約束第 2 條）。

### 資料層

- `item.enabled`（無此欄位一律視為啟用）＋ `disabledBy / disabledAt`；`isScheduleEnabled()`。**停用不釋放 Codify**（仍算已掛，`getSkillScheduleMap` 不變）——要放回可選清單只能刪除排程，沿用決議 19 的前置決策。
- `SCH_NOW`（mock 的現在 15:34）＋ `getWaitedMinutes/getWaitedLabel()`：等待時間是本頁最重要的催辦訊號，而 mock 的時間全是字串標籤，釘一個現在時刻才算得出「已等待 7h 42m」且不會每次重整就跳。
- `getDecisionQueue()`（等最久的排前面）、`getFailureQueue(items, ivs, acks)`（時間倒序，帶「後來補跑過沒有」）、`getScheduleStats()`（近 N 次完成／待決定／失敗＋平均時長）、`buildManualRun()`。
- `getScheduleStats` 的平均**排除「（含等待）」那幾筆**：那是人隔多久才來按，不是機器跑多久（不排除會算出「平均 10m 49s」這種看不出快慢的數字）。
- `getRecentHealth()` 移除（左欄不再顯示近 7 次失敗數，該資訊移到右欄排程 header），由 `getScheduleStats()` 取代。
- mock 補兩筆讓設計狀態有得看：**FDC 異常摘要新增一筆待決定的執行**（第二件才測得到「第一件展開、其餘收合」與「最久已等待」在比什麼）、**PM 到期提醒設為已停用**（停用態的灰點／下次執行「—」／只剩歷史）。
