# AI Chat 與 Ask AI 體系

**最高原則：被動查詢**。AI 僅在使用者主動發問時運作——不主動分析、不自動排序、不推播；所有行動由工程師確認後自行執行。唯一例外是 [Scheduling](scheduling.md)（受集體授權 + HITL 約束）。

## 四個入口

| 入口 | 位置 | Context |
|------|------|---------|
| AI Chat | AI 頁（Nav 第 5 位） | 課上下文 + 歷史對話 |
| AmbientBar | Dashboard 底部常駐 | 課上下文，對話個人私有 |
| Ask AI（Task） | Priority Feed 卡片 | Task 標題/優先級/說明/標籤/來源（完整文字） |
| Ask AI（KPI） | KPI toolbar | 僅報表定位（名稱/來源/更新時間），**不帶數值**——AI 自行用工具取即時資料 |

**互動規範**：任何 Ask AI 入口一律開**新對話**（`activeId = null`）；Input 上方藍色 Context Badge 預設收起、可展開、送出後自動清除。

## AntD 遷移

ChatPage UI 已於 2026-07-25 完成 **AntD 遷移 Phase 5**（見 [antd-migration-plan](../../concepts/antd-migration-plan.md)）：對話清單改 `List`（刪除加 `Popconfirm`）、Quick prompts 改 `Card`、**Context Badge 改 `Alert closable`**（關閉＝移除 context）、Skill 抽屜改 `Drawer`。對話泡泡保留自製（AntD 無 bubble 元件）。四個 Ask AI 入口帶 context 的行為不變。

## 2026-07-26 版面改版：當代 AI 對話

**PO**：「目前 ai 頁面的對話非常不理想，看起來很像 chatting 系統，不是當代的 ai 對話模式，例如不該出現 avatar、ai 的回應不需要氣泡。」

| | 改前 | 改後 |
|---|---|---|
| 頭像 | 雙方都有 | **全砍** |
| AI 回應 | 包在氣泡＋邊框裡 | **無氣泡無框、全寬純文字**（15px／行高 1.85／最大寬 720） |
| User 訊息 | 藍底白字實心塊 | 右對齊淡底圓角 |
| 訊息間距 | 16 | 32（讀起來像文件不像 IM） |
| 三態徽章 | 一顆大 Tag | 降級成一行細字 meta（**三輪已整個移除**，見下） |
| 工具呼叫 | 包框列表 | 灰色細行不包框；`✗ 已拒絕` 仍用紅字 |

此時徽章仍每則都在，只是視覺重量降低；到三輪才整個從 UI 移除，論證改由回應文字承擔。

## 五種情境腳本（2026-07-26 已實作）

`data/chatScenarios.js`。**對話標題直接就是該情境的目標**，demo 時不必另外解釋這串在演什麼。使用者的發言以底部「建議接話」按鈕呈現、**點了才推進**，AI 回合自動接上，遇到需要操作的東西才停下來等人。

| # | 標題（equipment） | 演什麼 | 對到哪條設計 |
|---|---|---|---|
| 1 | 執行 SPC 異常開單 SOP（中途需人工確認） | 呼叫 SOP → 寫入步驟停下 → 確認 → 成功開單 | HITL：寫入一律停下等人 |
| 2 | 執行 FDC 快速反應 SOP（API 變更導致失效） | 同上但**開單失敗**，AI 指出是 Case Center API v2→v3 導致標準元件失效並給修復方向 | [agent-skill-tiering](../../concepts/agent-skill-tiering.md) 風險 3「排程型 SOP 靜默失效」 |
| 3 | E-101 跳 ERR-4421 該怎麼處理 | 輔助 Skill 給明確建議 → user 要求改 SPC 管制上限 → **婉拒**並給兩個可點的操作 URL | Tool Gateway `[6]` 出場關的活體展示 |
| 4 | E-405 爐管跳 ERR-7702 該怎麼處理 | 無 Skill／SOP，依知識文件回答；user 問「能不能套用 ERR-4421 的做法」→ 拒絕並說明為何適用範圍只勾 CMP | 情境幻覺的反面教材 |
| 5 | E-502 CVD 跳 ERR-9105 該怎麼處理 | 無 Skill 也無知識 → 委婉說明並建議問資深同事 → **收斂成一張追蹤任務** | close loop：把「問不到」變成可追蹤的缺口 |

process／mfg persona 各有 2 個情境（SOP＋HITL、輔助問答拒絕執行／無知識建任務），equipment 為完整五個。

## 2026-07-26 第二輪：兩種互動模態 + 右側執行面板

PO 對照 Claude 的 `AskUserQuestion` 與 Cowork 右側 Progress 面板提了兩件事：決策彈窗太寬且沒有「其他意圖」的出口；值班的人需要隨時看得到 agent 的計畫與進度（SOP 可能跑 5–10 分鐘，「不想做帶有不確定性的等待，更不想等到結果才發現與想像不同」）。

### 互動模態從四種收斂成兩種

清點後發現當時同時存在四種：HITL 面板、行動按鈕「不用／好」、建議接話、舊資料的「確認提交／略過」。PO 判斷「核心兩種做法：對話式 or 統一的彈窗」，收斂後：

| 模態 | 用在哪 | 阻塞 |
|---|---|---|
| **對話式**（建議接話） | 建任務、一般追問 | ❌ |
| **決策卡**（統一） | 只給「會異動系統且流程卡住」的停點 | ✅ |

建任務**不能**塞進決策卡：它是非阻塞的附加動作，混進去會稀釋決策卡的份量——決策卡有力量正是因為它只在寫入被擋下時出現。三處 `action` 全部改寫成 user turn，走既有的建議接話機制，零新元件。

### 決策卡（原 HitlSheet）

從全寬 overlay bottom sheet 改成**對話流裡的卡片**：拿掉遮罩與 dimming（上面那些已完成的步驟與查到的數據，正是使用者做決定要看的東西，壓暗它是反效果），收進 720 欄，高度約砍半。新增三樣：**數字鍵 1/2/3**（值班速度）、**「我有其他指示…」**（收合成 chip、游標進輸入框）、**「稍後再決定」**（收合成 chip、不動輸入框）。兩個出口對到 Claude 的 `Type something else` 與 `Skip`；chip 常駐輸入框上方，流程不會消失。~~時限倒數~~ PO 指示先不做。

### 右側執行面板（`RunPanel`，寬 320）

**計畫來源是那份已核准 SOP 的 `plainSteps`，不是 AI 邊跑邊生的。** 這是與一般 agent 最大的差別：執行前就知道總共幾步、哪幾步會動到系統。四區——本次執行（SOP／生效狀態／步驟 N/M／計時）、執行計畫、這次的產出、這次用到的。

步驟六態：待執行／進行中／完成／等你決定／失敗／略過。兩個關鍵設計：**還沒跑到的 write 步驟預先標「會停下來等你確認」**（不確定性要在開始前消掉，不是在過程中安撫）；**條件分支未走的步驟標「本次不走（Level-2）」**，分支名從 `sop.graph.edges` 的 label 推導，不留白讓人猜。

預設關，偵測到 SOP 執行自動開，使用者關過之後同一則對話不再自動開。計時只在「真的在跑」或「停下等人」時走——那兩個時刻才是分秒必爭的時刻。

### 對話流瘦身（同一把尺）

| 元素 | 處置 |
|---|---|
| 工具識別碼 `spc.query_daily` | 砍（純工程 artifact） |
| io tag `讀取／計算／會異動` | 流裡砍，**搬到面板**——標在還沒跑到的步驟上才有意義 |
| 步驟明細 | 搬到面板 |
| 「這次的工具呼叫紀錄」整塊 | 降成一行 `🚫 已嘗試變更 SPC 管制界限，被系統擋下`；工具名與治理原因進面板 |
| 「查了這些現場數據」整塊 | **刪除**（證據已寫在 AI 的文字裡），資料改名 `evidence` 只餵面板 |
| 操作入口 | 從「標題＋說明＋URL」降成**一顆按鈕**；那串 `/app/...` 是我們自己看的 |
| Skill 名稱可點開 Drawer | 砍（面板取代）；`● 依核准流程 · XXX` 文字保留，那是信任論證 |
| 失敗的三層重複 | 分工：流裡 `✗ 失敗` / ResultCard 人話 / 面板技術細節 |

### 逐步播放

步驟一步一步跑出來（700ms／步，回合間 450ms），播放中「建議接話」disable。不這樣做「正在做什麼」只存在一瞬間，右側面板就沒有意義。

自由輸入仍未接模型，但**不再靜靜吃掉**：送出後 AI 誠實回一句「情境展示，自由輸入還沒接上模型」。

## 2026-07-26 第三輪：決策留痕、多任務面板、砍徽章

### 決策卡選完會留痕

原本選完卡片就消失，只看得到 AI 接著做事，回顧不到當時做了什麼決定。現在原位置留下 `✓ 已選擇：確認開立工單`（右對齊、綠框、比 user 氣泡輕），再接 AI 的執行結果。

### 操作按鈕只留在最後一則

PO：「使用者已經往下執行新的動作後，前面的按鈕還保留著會有衝突——這時可以按嗎？按了會從哪裡執行？該帶著按鈕之後的 context 嗎？」

`LinkButtons` 改成**只在最後一則訊息顯示**。但不是刪除——入口會永久落在右側「這次的產出」，否則跑完的工單就再也找不到。歧義消失、入口不流失。

### 執行面板改成兩層、支援多任務

原本 `buildRunPlan` 只找最後一個 SOP，同一則對話跑兩份會被蓋掉。改成 `buildRunSegments`：以 `skill.id` 變化切段，每段是第一層的一個「任務」，展開才看步驟。段狀態＝有 fail → 失敗／有 pause → 等你決定／有 running → 執行中／全部終態 → 已完成；預設只展開最後一段。計時併進任務列，且只在該段還活著時走。

情境 1 尾巴補了第二份 SOP（`sm-eq-007` 整理當班交接報告，純唯讀、不會停），用來對比「任務 1 停過一次要人確認、任務 2 一路跑完」，面板自然出現兩個任務。

**面板瘦身**（PO：「他們只在意執行了什麼 & 執行到哪」）：砍四顆 io tag、砍工具識別碼、砍 SOP 適用範圍攤開、砍步驟明細。明細只留兩個例外——**失敗的原因**（不能不給）與**分支未走的說明**。「這次的產出」「這次用到的」各自可收合；「這次用到的」只給 Skill／SOP 標題 + `›`，點開 `SkillPeekModal` 看詳情（purpose／適用範圍／步驟／說明，不做 Graph／Signoff／Ask AI，那些在 Setting 的全頁）。

兩種「需要人確認」的時態要分開，不能共用一句話：

| 步驟狀態 | 文案 |
|---|---|
| 已經停在這裡（`pause`） | `等待確認中…` ＋「去決定」按鈕 |
| 還沒跑到、跑到會停（`todo` + `needsConfirm`） | `需人工確認` |

### 三態徽章從 UI 移除 ⚠️

PO：「『依核准流程 · XXX』出現太多次，毫無意義干擾視覺。user 會預期『我能執行就表示系統中有核准的 SOP』。」

**這個論證對 `依核准流程` 成立，對另外兩態不成立**——`AI 依指引研判` 與 `一般回答` 講的是相反的事：這不是核准流程、責任在你。那是免責告知不是多餘的確認。

實際查過腳本後確認可以全砍：情境 3/4/5 的 AI 文字本來就都明說了（「這是依指引研判的建議，不是已核准的流程，最後判斷仍在你身上」「本課沒有 ERR-7702 的標準流程」「ERR-9105 完全沒有紀錄」）。

**代價：告知責任從 UI 轉移到模型的輸出規範。** 真實 LLM 不保證每次都講。因此 F-AI-01 的驗收條件必須加一條：**非核准流程的回答，必須在回應文字中聲明「這不是核准流程、責任在執行者」**，與既有的 KR1.3（來源版本標注 ≥90%）並列。Skill 類型資訊仍在右側面板的「這次用到的」保留得到。

## 2026-07-26 第四輪：產出區的定義與展開收合的可見度

**「這次的產出」只收真的做出來的東西。** 原本把失敗的結果卡也放進去，出現 `✗ 工單未開立 —— 這份 SOP 的第 5 步已經失效`——PO：「產物應該是真實發生才有，如果沒有就不產生。」失敗的位置在「執行任務」那一步的紅字與對話流的結果卡，不是產出清單。

連帶修正一個蒐集邏輯的錯：入口原本是跨則扁平收集，導致「手動開單／回報失效」這種**「你自己去做」的入口**混進產出。改成**跟著它自己那則訊息的產物走**——沒有成功產物的訊息，它的 links 不進產出區（仍留在對話流最後一則）。

**產物名稱本身就是連結**，右側 `↗` 表示會另開分頁；不再另外掛一顆按鈕（PO：「開啟任務按鈕有點多餘」）。

**展開收合的箭頭**原本是 10px `▾/▸` 擺在標題左邊，PO：「完全沒發現他是一個可以展開收合的功能」。對齊 Cowork 的 `Progress ⌄` 寫法改成：區塊標題的箭頭跟標題同字級、緊跟在標題右側（標題也從 11px 細字提到 13px）；任務列的箭頭同字級、靠最右。`⌃` 展開中／`⌄` 已收合。

## 2026-07-27 第五輪：左右職責互換，面板只剩計畫一層

**PO：「兩個紅框的資訊完全重疊，這樣做沒有意義。」** 清點後確認：左側流內步驟與右側面板步驟確實在講同一件事，只有「還沒跑到的那幾步」是右側獨有的（第二輪特地放進去的前瞻資訊）。

所以做法是**互換而不是單純刪除**——直接砍掉右側步驟會把唯一沒有重疊的價值一起砍掉：

| | 改前 | 改後 |
|---|---|---|
| 左側流內 | 只列已跑過的步驟 | **完整計畫**：未跑到置灰、跑到會停的預先標「跑到這步會停下來等你確認」、分支沒走的標「本次不走（分支名）」 |
| 右側面板 | 任務 → 展開看步驟（兩層） | **計畫一層**：這次要做幾件事、做到第幾件 |

前瞻資訊搬到使用者本來就在看的那一欄，比塞在 320px 側欄更看得到。**置灰的尾巴只長在最後一個 run 區塊**——往下走之後那些步驟已經有更新的紀錄，舊區塊還留著「待執行」會讓人以為它沒跑。失敗的技術細節（`HTTP 400 · unknown field "severity"` 與根因）也跟著回到流裡：面板不放步驟了，它沒有別的地方可去，也不該沒有地方去。

### 計畫改由 Orchestrator 開跑前宣告

`chatScenarios` 新增 `plan: { title, items: [{ key, skillId, title, tier }] }`。這是與前一輪最大的差別：計畫不再從跑過的訊息回推，而是**第一步開跑之前就整份宣告**——面板的價值來自「不做帶不確定性的等待」，邊跑邊冒出新項目就沒有這個價值了。

信任論證跟著變成**兩層**：計畫是 AI 組的（暫定），每一項的內容是已核准 SOP 的 `plainSteps`。計畫項目上**已核准 SOP 不標**（PO 的舊論證仍成立：能執行就表示核准過），非核准的項目才掛 `SkillTierTag`——目前腳本全是 SOP，這個標記還沒有情境用到。

情境 1 因此改寫成**一句話要跑兩份 SOP**（原本是兩次獨立請求）：使用者一次說完「跑 SPC 異常日報與開單，跑完把當班交接報告也整理好」，面板一開始就列出 2 項、第 2 項標「待執行」，決策卡結束後自動接上，不需要使用者再開口。

### 只留最新計畫，但產出照樣累積

PO 指定面板只保留正在執行或最後一次的計畫。**產出必須例外**——第三輪把對話流的操作按鈕收成「只在最後一則顯示」，交換條件正是「入口永久落在右側產出區」；計畫一換就清掉產出，那個交換條件會跳票。兩者性質本來就不同：計畫是「現在在幹嘛」，產出是「這段對話做出了什麼」。

### 三區改名：任務／產出／來源

PO 提議 Progress／Material／Context。**「這次的」確實要拿掉**（只留最新計畫之後，「這次」指這次計畫還是這段對話會產生歧義），但另外兩個詞沒有採用：

- `Material` 在設備課的日常語彙裡就是**備料**（同一份 SOP 在講「備料未齊 2 項」），跟工單／報表撞詞
- `Context` 語義準但是我們的行話；那一區真正的價值是「我要不要信這個結果」，用「來源」直指價值

另一個考量是全站語言一致性：nav 是英文，但**頁內區塊標題全是中文**，改英文會是頁內第一組英文標題，該當成全站決定而不是單一面板決定。

### 同輪第二次瘦身：面板只回答「做到第幾件」

看過畫面後 PO 再砍一輪：「左側在等待、右側也在等待，完全沒必要」「過多資訊反而造成認知負荷過重」。

| 砍掉的 | 為什麼 |
|---|---|
| 暫停項目的「去決定」按鈕 | 決策卡就在左側正中間，它自己就是入口 |
| 進度數字 `5/6`、`4/4` | 步驟在左邊看得到，右邊再數一次是同一件事講兩遍 |
| 計時 `00:09` | 同上；⚠️ **推翻**第二輪「計時只在真的在跑或停下等人時走」的決議 |
| 計畫標題摘要行 `… · 2/2 完成` | 標題在對話開頭講過了 |
| 已完成項目的「已完成」字樣 | ✓ 已經說完了 |

留下的只有：狀態圖示 ＋ 名稱 ＋（未完成時）一個狀態詞（執行中／已暫停／待執行／失敗）。**已完成的項目連狀態詞都不留**——這條規則的通則是：完成的事不需要再說一次完成，還沒完成的才需要說它現在怎麼了。

「等你決定」也改成「**已暫停**」：面板的角色是報狀態，不是催人行動；催人行動是決策卡的事。

**未實作**：計畫中途調整的留痕（`計畫已調整：新增…`）——目前沒有情境會觸發，不做沒人看得到的 UI。

## 「兩種 user，兩種語言」現在靠什麼守住

[agent-skill-tiering](../../concepts/agent-skill-tiering.md) 的論證沒有變——**工程師若分不出「照核准流程做」跟「照 AI 建議做」，每次採納都是在賭，他們會選擇不賭**。這是採用率問題不是資訊架構問題。

變的是它由誰承擔。三個階段：

| 時間 | 承擔者 |
|---|---|
| 2026-07-25 | 每則回答一顆大 Tag |
| 2026-07-26 一輪 | 降級成回應下方一行細字 meta |
| 2026-07-26 三輪 | **UI 不再標示；改由回應文字本身聲明，Skill 類型在右側面板的「這次用到的」查得到** |

**尚未實作**：SOP 卡片的「不適用」一鍵轉輔助判斷、飛輪 1 的「要不要變成 SOP？」提示、決策卡的時限倒數（PO 指示先不做）、「我有其他指示」輸入後真的改變 SOP 行為（目前只誠實說明未接模型）。

## 現況與缺口

UI 完整 ✅，**後端全 mock**。F-AI-01 目標：真實 LLM 串接（課上下文 system prompt）、對話後端持久化、**每則回答附 SOP 來源版本標注**（KR1.3 ≥90%）——對應設計原則「知識可信任」，見 [design-principles](../../concepts/design-principles.md)。

⚠️ **F-AI-01 新增驗收條件**（2026-07-26 三輪砍掉 UI 徽章後轉移過來的責任）：**非核准流程的回答，必須在回應文字中聲明「這不是核准流程、責任在執行者」**。UI 已經不會替模型講這句話了。

未來 EE/PE Agent 暫不實作；屆時異常判斷卡片**必須附判斷依據**（波形圖、數據來源），不得只給結論。
